# M3: Prove

Gate (PLAN §8): live probes confirm or refute each path, `fns prove` runs under
`id-verifier`, and the bundle verifies with Sigstore.

**Status: approved 2026-11-26 with two changes** (E1 and E4 below; see
`docs/DECISIONS.md`). The offline part (P1 to P4) is built. The live part
(P5) needs the lab and runs from a runbook.

## What M3 adds to the evidence

M2 stops at rung 1. M3 adds two rungs:

| Rung | Probe | What it asks | Run as |
| --- | --- | --- | --- |
| 2 evaluated | `arm-permissions` | `GET {scope}/providers/Microsoft.Authorization/permissions`: does the platform list this action for the caller at this scope? | test identity |
| 3 observed | `data-read` | a non-destructive data-plane read (`secrets/get`, `secrets/list`, `blob/read`) against the lab's synthetic data | test identity |

Probes run as the **test identity** (`sp-billing-agent` in the lab), because
they ask what *that* identity can do. The **verifier** runs as `id-verifier`, in
its own process. It never holds the test identity's credentials. It reads only
the frozen assertions, the journal and the artifacts the probes stored, and
it signs the result.

## The claim problem: a denial proves less than it seems

Most M2 failures are escalation paths. One example: Contributor on the RG gives
`vaults/write`, which can add an access policy, which then gives `secrets/get`.
A probe that tries `secrets/get` *now* and gets 403 does not refute that path,
because the path needs a write first.

So the verifier works per path, not per operation.

- At freeze time, every modeled path gets a list of the probes that **refute it
  if they return `denied`**:
  - A path with no escalation hop (only `assume-compromised`, `member-of` and
    snapshot facts before the final hop) whose final hop grants the operation
    directly can be refuted by the direct `data-read` probe, or by the
    `arm-permissions` check of that final hop's action.
  - A path whose final hop is indirect (`kv-control-to-data`, `listkeys-data`)
    can be refuted only by the check of its own action (`vaults/write`,
    `listKeys/action`). A direct-read denial does not refute it.
  - A path with an escalation hop (`owner-adds-credential`,
    `approle-self-grant`, `rbac-write`, `managed-identity` and so on) cannot be
    refuted in M3. Its first hop is a Graph or ARM write, and there is no
    non-destructive probe for it (E2).
- `must_not_reach` verdicts:

  | Probes say | Verdict | Coverage |
  | --- | --- | --- |
  | direct op observed `allowed` | `fail` | verified (`platform-gap` if rung 2 said denied) |
  | direct op evaluated `allowed`, no observed denial | `fail` | evaluated-only |
  | a modeled path is not refuted | `fail` | from the evidence that still supports it (modeled-only or evaluated-only); a direct denial goes in the reasons |
  | every path refuted, direct op observed `denied`, no open coverage surface | `pass` | verified (`model-gap` if the model had a path) |
  | every path refuted, direct op observed `denied`, an open coverage surface (for example PIM eligibility) | `inconclusive` | verified, naming the surface (E1) |
  | anything else | `inconclusive` | as the evidence allows |

- `must_still_do`: observed `allowed` gives `pass`; observed `denied` gives `fail`;
  evaluated `denied` gives `fail` (evaluated-only); evaluated `allowed` stays
  `inconclusive`. Write operations (`blob/write`) have no non-destructive probe
  in M3, so they reach rung 2 at best (E4).

The `Finding` validator already enforces the floor (no `pass` without an
observed result). The rules above are stricter, and `fns.verify` holds them
with tests.

## Frozen assertions

`fns prove` first builds the M2 report, then **freezes** an `AssertionSet`
*before any probe runs*. For each finding it records:

- the item, target, operation and modeled outcome;
- the paths, each with its id, its one-line rule summary and its `refuted_by` probe ids;
- the probes (`ProbeSpec`: id, kind, rung, scope operation, target, action, purpose);
- the open coverage surfaces for that operation.

The set also carries the contract thresholds, so the verifier computes the exit
code without the contract.

- Assertions are serialized as canonical JSON to `assertions.json`, and their
  sha256 is the run's assertion digest.
- The journal records a `freeze-assertions` step, whose response digest is the
  assertion digest, **before** any probe step.
- The verifier rejects a run if any of the following holds:
  - the file's digest differs from the journal;
  - a probe event precedes the freeze;
  - a probe step names a probe that is not in the frozen set;
  - an artifact's sha256 differs from its journal digest.

## Process and package boundary

```
fns prove (orchestrator: fns.prove)        python -m fns.verify (own process)
  contain -> report                          reads assertions.json
  freeze -> assertions.json + journal        opens journal.sqlite read-only (mode=ro)
  fns.probes: run each probe                 reads artifacts/<sha256>.json, checks digests
    -> artifacts/<sha256>.json + journal     computes findings, builds EvidenceBundle
  spawns the verifier with a scrubbed env    in-toto Statement -> DSSE -> signs
```

- `fns.verify` imports only `fns.models`. import-linter forbids:
  - `fns.adapters`, `fns.harden`, `fns.strike`
  - `fns.probes`, `fns.prove`, `fns.contain`
  - `fns.inventory`, `fns.journal`, `fns.scope`
  - `fns.cli` and the run modules

  It reads the journal with its own read-only SQLite connection and never uses
  the writer (E6).
- The orchestrator starts the verifier as a subprocess (`sys.executable -m
  fns.verify`) with every `AZURE_*`, `ARM_*`, `MSI_*`, `IDENTITY_*` and
  `GITHUB_TOKEN` variable removed. In live mode the verifier gets its own
  `id-verifier` credential through its own configuration (E7).

## Evidence bundle and signing

- `EvidenceBundle` (schema `schemas/evidence-bundle.schema.json`) holds:
  - the run id, mode and tenant
  - the assertion, contract, snapshot and report digests
  - the findings (the existing `Finding` model) and the summary
  - the artifact list
  - the verifier's identity label

  The bundle digest excludes `generated_at` and `tool_version`.
- The bundle is wrapped in an **in-toto Statement v1**:
  - the subjects are `assertions.json` and every artifact, by sha256;
  - the predicate is the bundle;
  - the predicate type is
    `https://github.com/danielguillaumont/fang-and-scale/blob/main/docs/predicates/prove-v1.md` (E8).
- It is signed as a **DSSE** envelope (`application/vnd.in-toto+json`).
- Signers:
  - `offline-test`:
    - An ephemeral Ed25519 key, from the `cryptography` package.
    - The public key goes in `signing.json`, and every output says
      `TEST SIGNATURE: integrity only, not identity, not Sigstore`.
    - It is used for tests, fixtures and `fns demo prove`.
  - `sigstore`:
    - Keyless signing with sigstore-python 4.x (`SigningContext`,
      `Signer.sign_dsse`), using the ambient OIDC token in GitHub Actions.
    - Verification uses `Verifier.verify_dsse` with an identity policy.
    - It is an optional extra (`uv sync --extra sigstore`) and is not run
      offline (E5).
  - `none`: writes the statement unsigned and says so.
- `python -m fns.verify check --run DIR` re-verifies the signature, every
  subject digest and the bundle digest.

## Phases

### P1. Models and freezing (offline)

`fns.models.assertions` (`ProbeSpec`, `PathAssertion`, `Assertion`,
`AssertionSet`) and `fns.models.bundle` (`EvidenceBundle`), with committed
schemas. In the contain report, a path's final hop gains an optional `check`
(the action and scope the probe should ask about). `fns.prove.freeze` turns a
report and a snapshot into an `AssertionSet`.

### P2. Probes (offline: interfaces and mocks)

`fns.probes`:

- **The `Probe` protocol.**
- **`MockProbe`:** replays a probe-results file labelled `FIXTURE`.
- **`ArmPermissionsProbe`:** builds the permissions request and evaluates the
  response, running through the scope gate under the `prove` verb with
  `arm:Microsoft.Authorization/permissions/read`. It is tested only with a
  mocked transport.
- **`DataReadProbe`:** an interface only. It raises `ProbeUnavailable` (the
  outcome is `not-run`) until the scope gate's vocabulary can name data-plane
  reads (E3).
- **The runner:** journals each probe as a read step keyed by its probe id and
  stores each observation content-addressed.

### P3. Verifier (offline)

`fns.verify`: inputs and integrity checks, verdict rules, bundle, statement,
DSSE, signers, and the `run` and `check` subcommands.

### P4. CLI and demo (offline)

- `fns prove --contract --snapshot --probes FILE [--out] [--sign]`
- `fns demo prove [--fixture DIR]`, which uses the bundled demo or
  `fixtures/lab-run-1` with its `probes.json` mock results; every line says
  FIXTURE
- `fns prove --check DIR`

### P5. Live (needs approval and the lab)

1. A scope gate vocabulary for data-plane reads, for example
   `kv:GET /secrets/{name}` and `blob:GET /{container}/{blob}`. Classified as
   reads, and allowed only for `prove` with principal ∈ `test_identities`. This
   is a gate change: plan first, with negative tests.
2. A test-identity credential flow for probes (a short-lived certificate on
   `sp-billing-agent`, created and removed by the runbook).
3. An `id-verifier` identity in the lab (Terraform), with Reader only.
4. Sigstore signing in CI with OIDC (`id-token: write` on that job only).
5. A runbook `docs/runbooks/m3-live-run.md`, and the gate run on the lab.

## Tests (negative first)

- **Freezing:**
  - the digest is stable and independent of input order;
  - every path gets the right `refuted_by` for its shape (direct, indirect,
    escalation);
  - a tampered file is rejected.
- **Verifier integrity:** rejects a digest mismatch, a probe before the freeze,
  an unknown probe id, a tampered artifact, and a journal opened for writing.
- **Verdict rules:**
  - a table covering every row above;
  - hypothesis: no `pass` on a `must_not_reach` without an observed denial and
    every path refuted;
  - hypothesis: adding an `allowed` observation never turns `fail` into `pass`.
- **Signing:**
  - DSSE PAE byte layout;
  - sign then verify round-trips;
  - a flipped byte in the payload or signature fails;
  - the test signature is always labelled.
- **Boundary:**
  - import-linter;
  - a test that the subprocess env contains no Azure variables;
  - a test that `fns.verify` source never opens the journal without `mode=ro`.
- **Determinism:** two `fns demo prove` runs give the same bundle digest, equal
  to the golden.

## Decisions (approved 2026-11-26)

- **E1 (changed).** A `must_not_reach` pass needs, beyond PLAN's observed
  denial, every modeled path refuted and no open coverage surface for the
  operation. PIM eligibility is a surface for every operation, so a PIM
  eligibility collector closes it: either the eligibility listings succeed
  (collected), or the tenant has no PIM and the snapshot records
  `pim-eligibility` as `not-applicable` together with the evidence (the API
  responses and the subscribed SKUs). It is never assumed; anything short of
  that evidence stays `not-collected`.
- **E2.** Escalation hops that need a write are not probed in M3, so paths
  through them cannot be refuted, and those items stay `fail`.
- **E3.** Data-plane probes need a scope gate vocabulary extension (P5.1);
  offline they are mock-only.
- **E4 (kept).** Write operations get no "authorization-only" probe in M3, so
  writes reach rung 2 at most. Research item R1 below asks whether one is
  possible.
- **E5.** Offline signing is an Ed25519 test signer that is always labelled.
  Sigstore is an optional extra, exercised only in CI with OIDC.
- **E6.** The verifier reads SQLite read-only and imports neither the journal
  writer nor the gate.
- **E7.** The verifier subprocess gets a scrubbed environment; live credentials
  for `id-verifier` come from its own configuration.
- **E8.** The predicate type URI points at a doc in this repository.

## Research (plan only, no live calls)

### R1. Does ARM authorize before it validates?

If ARM checks authorization before it validates the request body, a
deliberately invalid write is a non-mutating authorization probe: `403
AuthorizationFailed` means denied, and `400` (a validation error) means the
caller was allowed. That would lift writes such as `roleAssignments/write` or
`vaults/write` to rung 3 without changing anything.

Plan, to run only after approval and only in the lab:

1. For each write in the semantics table, pick an invalid body that ARM must
   reject before any side effect: for example a role assignment `PUT` whose
   `roleDefinitionId` is malformed, or a vault `PATCH` with an unknown SKU.
   The request must be invalid in a way no API version accepts, so it can
   never succeed by accident.
2. Send it as an identity that is **denied** (expect 403) and as one that is
   **allowed** (expect 400), and record the status, the error code and the
   body of both.
3. Repeat per resource provider and API version. The order is per provider,
   so one provider's result says nothing about another.
4. Check the Activity log for each request: a request that ARM rejected
   before authorization should show no write event.

Open points before any live call: the scope gate classifies these requests
as writes, so they need the `--approve <plan-hash>` flow (rule 1) even though
they are meant to fail; and a result counts only per provider and API
version, recorded in `docs/FINDINGS.md`.
