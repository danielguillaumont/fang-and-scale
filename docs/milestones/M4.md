# M4: Harden and detect

Gate (PLAN §8):

- record mode writes `must_still_do`;
- `fns harden` turns the contract green with legitimate use kept;
- each strike has a KQL rule and a detection result.

**Status: approved 2026-11-26** (H6 approved, H1 kept for v0.1; see
`docs/DECISIONS.md`). The offline part (K1 to K3) is built. The live part (K4)
needs the Entra P2 trial and Sentinel; the strikes (K5) need a plan and the
`--approve <plan-hash>` flow first.

## K1. Least-privilege minimizer (`fns harden`, offline, read-only)

`fns harden` proposes the **smallest Terraform diff** after which, in the model:

- no `must_not_reach` item fails, and
- every `must_still_do` item the model allowed before is still allowed.

It never applies anything. `--apply` stays unavailable until the
`--approve <plan-hash>` flow exists (rule 1).

- **Levers.** `fns.harden.tfmap` parses the lab's `.tf` files with a small
  parser for top-level blocks. It is not a general HCL parser, and it refuses
  constructs it does not understand. It finds the changes it can make:

  | Lever | Terraform change | Snapshot change it stands for |
  | --- | --- | --- |
  | `azurerm_role_assignment` | delete the block | remove the `hasRbacRole` edge (principal, role name, scope) |
  | `azuread_app_role_assignment` | delete the block | remove the `hasAppRole` edge (principal, Graph permission) |
  | `azuread_application.owners` with a workload SP | drop that list element | remove the `owns` edge |
  | `azurerm_storage_account.shared_access_key_enabled = true` | set it to `false` | set `allowSharedKeyAccess` to false |

  - A lever whose principal or scope cannot be matched to exactly one snapshot
    entity is reported as `unmapped` and never proposed.
  - Matching uses display names, and resource-name prefixes before `${...}`.
  - `for_each` and `count` blocks, and grants to `data.*` principals (the
    operator running `lab-up`), are skipped, and the output says so.
- **Search.**
  - Take the subsets of mapped levers that touch an identity the compromised
    principal controls, in increasing size (up to 4).
  - Run the M2 evaluator on the mutated snapshot for each.
  - Keep the smallest size that satisfies the contract. Propose the lexically
    first set of that size, so the output is deterministic, and list the other
    sets of the same size as alternatives.
  - If no subset of size 4 or less works, say so; do not fall back to a
    heuristic.
- **Output.**
  - A unified diff against `lab/*.tf`.
  - The before and after summaries: critical count and still-do status.
  - The levers chosen, with the paths each one breaks.
  - `plan sha256:<hash of the diff>`, the value a future `--approve` takes.
  - Every line says `modeled`: a proposal is rung 1 until M3 probes confirm it.
- **Not in M4 offline: replacing a role with a narrower one** (for example
  Contributor with a custom role). Removal and settings only (H1).

## K2. Record mode (`fns record`, offline parser)

- **Input:** one or more JSON files of log rows, as exported from Log Analytics
  (an array of rows, each with a `Type`), plus the object ID of the identity to
  record.
- **Recognised rows:**

  | `Type` | Field | Contract operation |
  | --- | --- | --- |
  | `StorageBlobLogs` | `OperationName` GetBlob, GetBlobProperties | `blob/read` |
  | `StorageBlobLogs` | `OperationName` PutBlob, PutBlock, PutBlockList, AppendBlock | `blob/write` |
  | `AzureDiagnostics` (Key Vault `AuditEvent`) | `OperationName` SecretGet, SecretList, SecretSet | `secrets/get`, `secrets/list`, `secrets/set` |
  | `AzureActivity` | `OperationNameValue` `.../LISTKEYS/ACTION` | `listKeys` |
  | `AzureActivity` | `OperationNameValue` `.../ROLEASSIGNMENTS/WRITE` | `roleAssignments/write` |

  Entra `AuditLogs` rows are recognised as directory operations. They are
  **reported, not written**, because `must_still_do` in contract v1 holds
  resource targets only (H3).
- **Filtering:**
  - Only successful rows by that identity are recorded: status 2xx,
    `ResultSignature` OK or `ActivityStatusValue` Success.
  - Failed rows are counted.
  - Unknown operations are listed as `unmapped` and never dropped silently.
- **Output:**
  - `must_still_do` items with `source: recorded`, targets by resource name
    (not ARM ID, so no subscription GUIDs reach a committed contract; H4),
    sorted.
  - With `--contract`, the items are merged into that contract and written to
    `--out`. An item that collides with a `must_not_reach` entry is reported and
    left out: the contract model rejects the overlap.
- **Tests** use hand-written sample logs under `tests/harden/data/`. They are
  not recordings, and the M4 live run records real ones.

## K3. Detection rules as code (`detections/`)

- **Format.** One YAML file per rule. Fields: `id`, `title`, `severity`,
  `tactics`, `covers` (contain rules and operations it detects), `tables`, `query`
  (KQL), `query_frequency`, `query_period`, `entity` columns, and `parameters`
  (for example the monitored identities).
- **`fns detections export`** renders Sentinel scheduled alert rule bodies
  (`Microsoft.SecurityInsights/alertRules`, kind `Scheduled`) as JSON. It does
  not deploy them; that is K4.
- **Structural tests** (no workspace needed):
  - every file validates;
  - ids are unique;
  - the KQL starts with a declared table and has balanced brackets and quotes;
  - every `{{parameter}}` is declared and every declared parameter is used;
  - there is no `search *` and no `union *`;
  - entity columns are projected;
  - frequency ≤ period.
- **Coverage test:** every escalation rule in `fns.contain` and every operation
  in the semantics table is covered by at least one rule, or listed in
  `detections/EXEMPT.yaml` with a reason (H5).

## K4. Live (needs approval, the P2 trial and Sentinel)

- Log Analytics plus diagnostic settings in Terraform: Activity Log, Entra
  audit/sign-in, Key Vault and Storage.
- Deploy the rules.
- Run the four lab strikes from K5 and record a detection result for each.
- Record mode on the real logs, then `fns harden` on the new contract, then
  M3 `fns prove`, so the green result is observed, not only modeled.

## K5. Lab strikes (moved from M6, H6 approved)

Four non-destructive strikes, run as the test identity against the lab only:

| Strike | Write | Cleanup |
| --- | --- | --- |
| listKeys | `POST .../storageAccounts/{name}/listKeys` (reads keys, changes nothing) | none |
| vault write | a tag on the vault through `vaults/write` | remove the tag |
| owner adds credential | a short-lived password on the owned application | delete the credential |
| app role self-grant | an app role assignment on the owned service principal | delete the assignment |

Each one is a write (rule 1), so `fns strike` needs the `--approve <plan-hash>`
flow, a journaled cleanup step for each write, and a plan you approve before
any code. Nothing here is built yet.

## Roadmap after v0.1

- **Narrow to a custom role.** When removal cannot satisfy a contract (one
  role grants both a kept read and a forbidden write), propose a custom role
  with only the kept actions, instead of "no proposal" (H1).

## Decisions (approved 2026-11-26)

- **H1 (kept for v0.1).** The minimizer only removes grants or tightens
  settings. Narrowing to a custom role is on the roadmap above.
- **H2.** The search is exact up to 4 levers, with no heuristic fallback.
  Matching is by name and prefix, and anything ambiguous is unmapped.
- **H3.** Recorded directory operations are reported, not written, because
  `must_still_do` cannot hold `directory: tenant` in contract v1.
- **H4.** Recorded targets use resource names, not ARM IDs.
- **H5.** Detection coverage is enforced by a test, with an explicit exemption
  file.
- **H6 (approved).** The four non-destructive lab strikes (listKeys, vault
  write, owner adds credential, app role self-grant) move into M4 as K5.
