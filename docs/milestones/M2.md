# M2: Contain (Antivenom)

Gate (PLAN §8): `fns contain` fails the seeded contract and prints each
escalation path with rung labels and coverage.

**Status: approved 2026-11-26, with D1 to D5 as written.**

Progress: C2 (reach engine) and C3 (paths, `ContainReport`, `fns contain`,
`fns demo contain`) are done on fixtures. C1 collectors are prepared with
mocks; the live C1 recording and the C4 gate need the lab
(`docs/runbooks/m2-live-run.md`).

M2 is read-only and offline. `fns contain` reads a snapshot and a contract and
calls no API. The live parts are C1 (a richer `fns scout`) and the final gate
run against the lab, which stays up from M1.

## What M2 can and cannot claim

M2 produces rung 1 evidence (**modeled**) only. Rungs 2 and 3 need test-identity
credentials, which arrive in M3. So the rule for M2 is:

> **The model can make a finding fail. It can never make one pass.**

| Item | Model says | Verdict | Coverage | Notes |
| --- | --- | --- | --- | --- |
| `must_not_reach` | reachable | `fail` | `modeled-only` | with the shortest path(s) and the facts each hop rests on |
| `must_not_reach` | not reachable, every fact it needs collected | `inconclusive` | `modeled-only` | "not reachable in the model; needs an observed denial (M3)" |
| `must_not_reach` | depends on something not collected | `inconclusive` | `not-assessed` | names the `not_collected` surface, for example PIM eligibility or RBAC conditions |
| `must_still_do` | not allowed | `fail` | `modeled-only` | nothing grants the legitimate operation |
| `must_still_do` | allowed | `inconclusive` | `modeled-only` | "allowed in the model; needs an observed success (M3)" |
| any | target unresolved or ambiguous, or unknown operation semantics | `inconclusive` | `not-assessed` | rule 4 |

The evidence model already rejects a `must_not_reach` pass without an observed
denial. A new test holds the stronger M2 invariant: across random snapshots and
contracts, `fns contain` never emits `pass`.

**Decision D1, needs your approval.** In M2, a `must_still_do` item that the
model allows comes out `inconclusive`, not `pass`. The trade-off: every contract
with legitimate-use items reports some inconclusives until M3. The alternative
is `pass` labelled `modeled-only`. That reads better, but it claims legitimate
use works without having observed it.

## Contract semantics M2 has to define

These are the semantics A2 deferred (flag 15).

- **Critical.** Every failed `must_not_reach` finding is critical.
  `max_critical_reachable` counts them. A failed `must_still_do` always fails the
  contract and is not budgeted.
- **Exit codes.**
  - `1`: critical findings exceed `max_critical_reachable`, or any
    `must_still_do` fails.
  - Otherwise `3`: inconclusive findings exceed `max_inconclusive` and
    `on_inconclusive: fail`.
  - Otherwise `0`, with a warning line when `on_inconclusive: warn` is what saved
    it.
  - Usage and input errors stay `2` and `1`, as in M1.
- **`directory: tenant` + operation means "on any object in the tenant".** Being
  able to do it to a single app counts as reachable. This is a blast-radius tool:
  adding a credential to one privileged app is the escalation. **Decision D2.**
- **Short names.** A name is matched case-insensitively against `display_name`
  among entities of a compatible type (`resource` for `resource:`,
  service principal or managed identity for `assume_compromised`). Zero matches or
  more than one means `inconclusive`. Full ARM IDs and object IDs always work.
- **Operation vocabulary.** `src/fns/contain/semantics.py` is a table that maps
  each contract operation to what grants it:

  | Contract operation | Granted by |
  | --- | --- |
  | `secrets/get` | data action `Microsoft.KeyVault/vaults/secrets/getSecret/action` (RBAC-mode vault) or an access policy with `get` |
  | `secrets/list` | data action `Microsoft.KeyVault/vaults/secrets/readMetadata/action`, or an access policy with `list` |
  | `listKeys` | action `Microsoft.Storage/storageAccounts/listKeys/action` |
  | `blob/read`, `blob/write` | data actions `.../blobServices/containers/blobs/read` and `/write` |
  | `roleAssignments/write` (resource) | ARM `Microsoft.Authorization/roleAssignments/write` |
  | `roleAssignments/write` (tenant) | Entra directory role assignment |
  | `applications/credentials/update` (tenant) | adding a password or key to an application |

  An operation not in the table is `inconclusive` ("unknown operation
  semantics"), never `pass`. The table is versioned and has a test per row.

## Reach model

`src/fns/contain/`. Pure functions over a `Snapshot`, with no I/O and no imports
from `fns.adapters`. Import-linter enforces both.

1. **Principal closure.** Start from the compromised identity. Add its groups
   (`memberOf`, transitively) and every identity it can become. Iterate the
   rules below to a fixed point, and record a justification on every derived
   capability.
2. **Escalation primitives.** These are PLAN §2's list, implemented now:

   | Rule | Needs | Grants |
   | --- | --- | --- |
   | `owner-adds-credential` | owns application X, plus Graph `Application.ReadWrite.OwnedBy` or `.All` | acts as every SP that is an `instanceOf` X |
   | `app-readwrite-all` | `Application.ReadWrite.All` | acts as any SP whose application is in the tenant |
   | `approle-self-grant` | `AppRoleAssignment.ReadWrite.All` | any Graph app permission (then re-evaluated) |
   | `rolemanagement-write` | `RoleManagement.ReadWrite.Directory`, or the Privileged Role Administrator or Global Administrator directory role | any directory role, which covers `roleAssignments/write` (tenant) |
   | `rbac-write` | `Microsoft.Authorization/roleAssignments/write` at scope S | Owner at S |
   | `listkeys-data` | `listKeys` on a storage account, unless `allowSharedKeyAccess` is false | blob read and write on that account |
   | `kv-control-to-data` | `Microsoft.KeyVault/vaults/write` | secrets data access: it can switch the vault to access-policy mode or add an access policy |
   | `managed-identity` | `Microsoft.Compute/virtualMachines/runCommand/action`, or Automation runbook write, on a resource with an identity | acts as that resource's managed identity |

   An identity that can act as another identity keeps all of its own grants.
3. **Azure RBAC evaluation**, for a principal set, an action and a target:
   - Assignments come from the target and its ancestors, compared as parsed
     segments (the same parser as the gate, never string prefixes).
   - A definition grants the action when an `actions` or `dataActions` pattern
     matches it and no `notActions` or `notDataActions` pattern does.
     Patterns are case-insensitive globs.
   - Deny assignments subtract. Excluded principals and
     `doNotApplyToChildScopes` are honoured.
   - An assignment with a `condition`, or any surface listed in `not_collected`
     that could change the answer, makes the result `inconclusive`. It is never
     silently allowed or denied.
4. **Paths.** NetworkX `MultiDiGraph` (added as a runtime dependency, per the
   CLAUDE.md stack). For each failed item, the shortest path and up to 3
   alternatives, in deterministic order. Every hop carries the snapshot edge or
   rule it rests on and that fact's `source_api`.

## Outputs

- **Rich (default).** A table per contract item: verdict, rung, coverage,
  target, operation. Then, for each failure, the path:
  ```
  FAIL  directory:tenant  roleAssignments/write   modeled · modeled-only
    sp-billing-agent ─owns→ app-escalation-target            [graph.owners]
      ─owner-adds-credential (Application.ReadWrite.OwnedBy)→ acts as app-escalation-target
      ─approle-self-grant (AppRoleAssignment.ReadWrite.All)→ RoleManagement.ReadWrite.Directory
      ─rolemanagement-write→ roleAssignments/write on tenant
  ```
  Coverage comes first in the summary (PLAN §5.5), then
  `critical reachable: N/max · inconclusive: N/max`.
- **`--json PATH`.** A new `ContainReport` model with a schema committed as
  `schemas/contain-report.schema.json`. It holds the contract digest, the
  snapshot digest and mode, the findings (the existing `Finding` model), the
  paths, and the semantics table version. The report digest follows the same
  rules as the snapshot digest, and FIXTURE mode carries through. **This changes
  the evidence model, so decision D3:** `Evidence` gains an optional `path_id`
  that references a path in the report.
- **CLI.**
  - `fns contain --contract FILE --snapshot FILE`. No "latest" magic: the
    snapshot is explicit.
  - `fns demo contain`, which replays the bundled demo fixture end to end. Every
    line is labelled `FIXTURE`.

## Tests (with the code, negative tests first)

- **Semantics:** one test per table row; an unknown operation gives
  `inconclusive`.
- **RBAC evaluator:**
  - a table covering wildcard, `notActions`, data versus control plane, deny
    assignment with exclusions and the child-scope flag, a condition (gives
    `inconclusive`), and sibling RG and prefix lookalikes (`rg-lab` and
    `rg-lab-prod`), which are not ancestors;
  - hypothesis: agreement with an independent brute-force oracle on random
    small role sets.
- **Rules:** one positive and one negative test per primitive. Hypothesis checks
  that the fixed point terminates and does not depend on rule order.
- **Monotonicity (hypothesis):**
  - adding an edge or grant never turns a `must_not_reach` from `fail` to
    anything else;
  - removing a grant never creates a new failure.
- **Never pass (hypothesis):** random snapshot plus contract gives no `pass`.
  Totality: no crash on any valid snapshot.
- **Determinism:**
  - permuting snapshot input order leaves the report digest unchanged;
  - two `fns demo contain` runs give the same digest, equal to the golden one.
- **Paths:** every hop maps to a real snapshot edge or a rule application; the
  shortest path is first.
- **Mutation-lite** (before M5): on the demo snapshot, removing each seeded
  grant flips exactly the expected item away from `fail`.
- **Import boundary:** `fns.contain` imports nothing from `fns.adapters`,
  `fns.scope.credentials`, `fns.strike` or `fns.harden`.
